# Improve MOQX-client mixed stream/control pressure

Status: ready-for-agent
Type: AFK
Category: performance

## Parent

`.scratch/transport-layer-foundation/issues/26-harden-transport-pressure-abstractions.md`

## What to build

Diagnose and improve the remaining MOQX-client caller-side stream/control
pressure gap after the DATAGRAM path was reclassified as close enough.

The next v1 product target is caller-side MOQ behavior: connect out, publish or
subscribe over streams, and keep control traffic healthy while object-like
streams are under pressure. Listener/relay performance is explicitly out of
scope for the current harness, and QUIC DATAGRAM tuning should not be reopened
unless a concrete draft-14 interop bug appears.

The current x86-control evidence from run
`20260609T093717Z-issue40-x86-control-mixed-pressure-32x1000-1` shows a real
stream/control gap on a controlled path:

- workload: 32 object-like streams, 1000 x 1180-byte payloads per stream, and
  100 x 64-byte control messages at 100 messages/sec;
- reference `quicprobe -> quicprobe`: 116.99 Mbps, control p99 37.95 ms, no
  break symptom;
- `moqxprobe -> quicprobe`: 73.37 Mbps, control p99 139.43 ms, no break
  symptom;
- the old mailbox artifact is gone: final `message_queue_len=0`, peak 497,
  32,000 object send completions, 100 control send completions, and zero
  pending object/control completions.

This issue should make the mixed stream/control loop the new performance
progress tracker, equivalent to what #40 did for DATAGRAM.

## Acceptance criteria

- [ ] Reproduce the mixed stream/control gap on the active x86-control lab, or
      on a fresh controlled lab if the current one has been torn down, with a
      same-run iperf3 baseline and healthy `quicprobe -> quicprobe` reference.
- [ ] Capture at least two clean same-shape repetitions before changing code so
      normal lab variance is separated from implementation behavior.
- [ ] Classify the first bottleneck hypothesis from evidence: benchmark mixed
      scheduler, object stream sender, control stream scheduling, stream
      send-completion cadence, receive/event pump, telemetry collector,
      binary validation/allocation, quicer/MsQuic stream behavior, or reference
      peer behavior.
- [ ] Add only low-overhead diagnostics needed to prove or falsify that
      hypothesis, keeping `transport-bench-v1` summaries stable and putting
      richer detail in diagnostics/sidecars when needed.
- [ ] Preserve the async stream send model and explicit completion accounting;
      do not hide backpressure by making `send_stream/4` wait for peer
      delivery.
- [ ] If implementation changes are made, rerun the controlled comparison
      against the same reference workload and record whether goodput, control
      p99, mailbox pressure, completion counts, and break symptoms improved.
- [ ] Define the next stop point in evidence terms. For the current 32-stream
      mixed shape, a reasonable first "close enough" threshold is MOQX goodput
      at least 80% of the same-run reference and MOQX control p99 no worse
      than 2x the same-run reference for two clean repetitions, with no break
      symptom, zero pending completions, and bounded final mailbox depth.
- [ ] Record each round in #26 with run id, artifact versions, lab topology,
      reference result, MOQX result, any rejected knobs, and whether the lab
      remains alive or was destroyed.

## Notes

The first useful step is evidence, not a fix: repeat the mixed pressure run on
the currently alive x86-control lab while the artifacts and path are still
available. If the gap reproduces, compare pure stream pressure and mixed
stream/control pressure to decide whether the problem is object-stream
throughput alone or control traffic interference under object pressure.

Keep local loopback runs labeled as calibration only. Use controlled remote
evidence for performance claims.
