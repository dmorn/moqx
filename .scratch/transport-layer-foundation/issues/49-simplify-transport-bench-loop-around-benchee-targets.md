## Context

The current transport benchmark stack grew from the need to run controlled
real-path experiments on disposable hosts. It now includes Terraform-based
Hetzner provisioning, `probed` as a remote control plane, release/deploy
scripts, suite orchestration, a shared JSONL ledger format, telemetry-backed
summary collection, and multiple historical benchmark entrypoints.

That machinery was useful while discovering the problem space, but it is now
slowing down the main performance loop. The near-term product target is
caller-side `moqx` performance: publishing or subscribing against an external
QUIC/MOQT peer. For that work, the fastest loop is a local Benchee runner that
can compare multiple client implementations against configurable targets:

```text
target=fake
target=quicprobe host=127.0.0.1 quic_port=<port> iperf_port=<port>
target=quicprobe host=<remote> quic_port=<port> iperf_port=<port>
```

The operator can keep one or more simple benchmark servers running with only
`iperf3` and `quicprobe` installed. The local benchmark runner owns client
implementation selection, target parameters, telemetry capture, optional pcap
capture, and Benchee output. This intentionally trades some lab purity for a
much tighter iteration loop while tuning caller-side process architecture.

## What to build

Refactor the benchmark area so `bench/moqxprobe` becomes a slim Elixir
benchmark library and Benchee script collection for caller-side QUIC client
implementations.

The new architecture should keep `bench/quicprobe` as the reference QUIC peer,
remove the long-lived remote orchestration/provisioning stack, and treat
targets as explicit CLI data rather than infrastructure state. The benchmark
runner should support fake-transport runs for process-model isolation and
real-transport runs against local or remote `quicprobe` by passing host and
ports as flags.

`iperf3` remains a target preflight/baseline tool. It should not be a measured
Benchee job in the hot benchmark matrix. A run may record the `iperf3` result
as sidecar metadata so QUIC measurements can still be interpreted relative to
the path ceiling.

## Proposed architecture

```text
bench/
  quicprobe/
    repo-owned Go/quic-go reference peer

  moqxprobe/
    Elixir benchmark clients
    Benchee scripts
    target adapters
    local telemetry summaries
    optional pcap/flamegraph helpers
```

Client implementations should be comparable as Benchee jobs, for example:

```text
context_owner_stream
stream_owner_stream
future_paced_stream
future_datagram_sink
future_batched_datagram_sink
```

Targets should be comparable as Benchee inputs or explicit script options, for
example:

```text
fake
quicprobe://127.0.0.1:<quic_port>?iperf_port=<iperf_port>
quicprobe://<remote_host>:<quic_port>?iperf_port=<iperf_port>
```

The exact CLI syntax can change during implementation, but experiment setup
must be flag-driven. Do not use mutable `Application` env or hidden global
configuration for target selection or benchmark parameters.

## What to remove or archive

Remove the pieces that only exist to support the old disposable remote lab
loop:

- `bench/infra/hetzner` and related Terraform provisioning documentation.
- `bench/probed` and its HTTP daemon/control-plane model.
- Remote release/deploy/suite scripts that build around `probed`, Terraform
  run ids, SSH deployment, or remote artifact bundles.
- `just` recipes whose only purpose is provisioning, deploying, driving, or
  tearing down the old Hetzner/probed lab.
- Documentation and project skill text that describes the old remote lab as
  the default benchmark workflow.

Archive rather than preserve as active contracts:

- `transport-bench-v1` JSONL as the canonical output format for new benchmark
  work.
- The shared ledger project if it is only needed by `transport-bench-v1`.
- Telemetry collection paths whose primary purpose is reconstructing the old
  JSONL summary format.
- Historical reports and metrics documentation that describe the old remote
  suite loop.

Archiving can mean moving content under a clearly named legacy/archived
location or deleting generated/obsolete tooling after any useful decisions have
been copied into current docs. The end state should make the active benchmark
loop obvious to a new contributor.

## Acceptance criteria

- [x] `bench/moqxprobe` has a documented Benchee-based benchmark loop for
      caller-side client implementations.
- [x] Benchmark setup is controlled by explicit flags for target host, QUIC
      port, optional `iperf3` port, workload shape, implementation selection,
      and measurement duration.
- [x] Fake-transport benchmarks remain available for process-model
      calibration without claiming real-network evidence.
- [x] Real-transport benchmarks can target either local or remote `quicprobe`
      using the same client implementation matrix.
- [x] `iperf3` can be run as a target baseline/preflight and recorded as
      metadata, but it is not mixed into Benchee job timing.
- [x] The active docs no longer point operators to Terraform/probed/release
      deployment as the default benchmark loop.
- [x] Old infrastructure, remote-control, and deploy orchestration code is
      removed or archived so it cannot be mistaken for the current path.
- [x] Previous metrics collection and `transport-bench-v1` formatting are
      explicitly marked legacy/archived unless a current Benchee-side artifact
      still depends on them.
- [x] The remaining benchmark artifact story is intentionally small: Benchee
      results plus optional sidecar metadata for target, git SHA, `iperf3`
      baseline, telemetry summaries, and capture paths.
- [x] The project benchmark skill and `.scratch/transport-layer-foundation/PRD.md`
      reflect the new direction after the cleanup lands.

## Blocked by

Human review of the cleanup boundary. This issue intentionally removes a lot
of previously built benchmark infrastructure, so implementation should start
only after confirming which old artifacts must be archived versus deleted.

## Notes

This issue does not decide final production benchmark methodology. A stricter
disposable lab can be reintroduced later as a final validation layer if the
local-runner loop produces a candidate client architecture worth validating.

The near-term goal is faster iteration on `moqx` as a caller. Listener/relay
performance remains future work.
