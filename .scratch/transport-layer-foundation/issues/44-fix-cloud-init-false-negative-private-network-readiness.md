# Fix cloud-init false-negative in private-network readiness

Status: closed
Type: AFK
Category: bug

## Parent

`.scratch/transport-layer-foundation/issues/42-build-probed-remote-control-plane.md`

## Problem

Hetzner benchmark nodes can sometimes report `cloud-init status: error` even
though the private network route is present, the peer is reachable through the
private network, and the required benchmark toolchain is installed.

This creates a bad operator failure mode: `just bench-transport-private-check`
fails early because it treats cloud-init success as the proxy for readiness, but
the real benchmark preconditions may already be satisfied.

This is distinct from #25. Issue #25 fixed the case where the private interface
or route was actually unusable. This issue is about avoiding a false negative
when cloud-init reports an init-local/network-config error while the private
path itself works.

## Evidence

During x86-control run `20260608T131235Z-iter-remote`, Terraform provisioned:

- client: `168.119.96.235`, private IP `10.88.0.11`, `fsn1`, `ccx23`
- server: `77.42.64.162`, private IP `10.88.0.12`, `hel1`, `ccx23`

Initial SSH to the client timed out while the node was still coming up, but a
later SSH check succeeded. The client then reported:

```text
status: error
extended_status: error - done
detail: DataSourceHetzner
errors:
  - can only concatenate str (not "NoneType") to str
recoverable_errors:
ERROR:
  - failed stage init-local
WARNING:
  - network-config-v1 failed schema validation!
```

At the same time, the private routes existed:

```text
client -> server: 10.88.0.12 via 10.88.0.1 dev enp7s0 src 10.88.0.11
server -> client: 10.88.0.11 via 10.88.0.1 dev enp7s0 src 10.88.0.12
```

The required client-side tools were also present:

- `go version go1.26.4 linux/amd64`
- `Elixir 1.19.5` on `Erlang/OTP 28`
- `iperf3 3.16`

The practical observation from repeated remote runs is that this cloud-init
error can coexist with a usable private network, so the readiness check needs
to separate "cloud-init is clean" from "the benchmark path is usable."

## What to build

Make the Hetzner readiness flow distinguish three things explicitly:

1. SSH/bootstrap reachability.
2. Actual benchmark readiness: private peer routes, private ICMP/TCP
   connectivity, and required tools.
3. Cloud-init diagnostic status.

The readiness check should fail when the private path or toolchain is unusable.
It should not fail solely because cloud-init reports an error that is proven
not to block the benchmark preconditions.

## Acceptance criteria

- [x] Reproduce the cloud-init false-negative on a disposable Hetzner run, or
      document why it no longer reproduces.
- [x] Capture the relevant cloud-init diagnostics in the run results when
      cloud-init reports `error`.
- [x] `bench-transport-private-check` verifies private peer routes and proves
      client-to-server ICMP and TCP connectivity over the private IPs even when
      cloud-init status is non-clean.
- [x] The readiness output clearly reports cloud-init status as diagnostic
      evidence instead of conflating it with private-network failure.
- [x] The check still fails if SSH is unavailable, required tools are missing,
      peer routes are absent, ICMP fails, or private TCP fails.
- [x] `bench/infra/hetzner/README.md` documents the distinction between
      cloud-init diagnostics and benchmark readiness.
- [x] Existing private-network readiness tests or shell checks are updated so
      this does not regress silently.

## Non-goals

- Do not relax the actual benchmark path requirements.
- Do not remove cloud-init diagnostics.
- Do not treat all cloud-init failures as harmless; only tolerate them after
  proving the concrete benchmark prerequisites.

## Notes

The likely fix is not to ignore cloud-init. The cleaner model is to collect
cloud-init status for evidence, then validate the actual path and toolchain
directly. If the root cause is in our generated network config, fix it; if it
is a Hetzner/cloud-init interaction that leaves the path usable, document and
tolerate it as a warning.

## Resolution

Implemented the readiness check as a separate script:

```text
bench/infra/hetzner/scripts/private_check.sh
```

`just bench-transport-private-check` now resolves Terraform outputs and calls
that script. The script records cloud-init status under
`bench/moqxprobe/results/<run-id>/private-check/`, reports non-clean
cloud-init as a warning, and decides benchmark readiness from concrete checks:
SSH reachability, Go/Elixir/`iperf3` availability on both nodes, peer-private
routes in both directions, client-to-server private ICMP, and client-to-server
private TCP `iperf3`.

Added a fake-SSH shell regression:

```text
bench/infra/hetzner/scripts/private_check_test.sh
```

The regression simulates `cloud-init status: error` while concrete readiness
checks pass, and also proves the script still fails when the required toolchain
is missing.
