## Why this is needed

We have redesigned benchmark measurement more than once, and the latest
`flow_partitions` work exposed that we are still too summary-first.

The current active benchmark loop is useful:

- `bench/moqxprobe` compares caller-side client implementations with Benchee;
- fake targets isolate process-model and OTP architecture effects;
- `quicprobe` targets provide receiver-side delivery evidence;
- `iperf3` gives a path preflight/baseline;
- delivery evidence is collected outside the measured Benchee function.

But the current output still makes it too easy to collapse several different
questions into one ambiguous number:

- Benchee `ips` answers how many whole benchmark invocations completed per
  second. Depending on the script, that invocation may include connection
  setup, stream creation, sender loop work, local send-completion draining, and
  other client-side work.
- Receiver evidence currently validates final aggregate counts: bytes,
  streams, DATAGRAMs, and errors. It proves delivery, but not delivery shape.
- Manually derived "Gbps" values divide known payload bytes by a chosen
  duration. Without naming the denominator, those numbers can be mistaken for
  steady-state bandwidth, receiver bandwidth, path utilization, or wire rate.
- Averaging over the entire invocation hides delivery patterns: bursty sends,
  drain lag, receiver stalls, and backpressure can all produce the same final
  bytes/time ratio.
- `payload_count` and stream write events are not packets. Reporting `pkts/s`
  without packet capture or QUIC stack packet counters would be false
  precision.
- Local/fake/loopback results can be useful calibration, but they must not be
  presented with the same confidence as remote-path evidence.

This matters because performance work is about locating the bottleneck, not
only ranking implementations. A benchmark can be CPU-bound in the BEAM,
blocked on process mailboxes, limited by NIF/send admission cost, saturating
UDP socket buffers, pacing poorly on the wire, or simply constrained by a bad
network path. One average bandwidth number cannot distinguish those cases.

The contract should follow Brendan Gregg-style performance thinking:

- start from the question being answered;
- separate utilization, saturation, and errors per resource;
- keep instrumentation overhead bounded and visible;
- collect enough evidence to move from symptom to bottleneck without turning
  the observer into the workload.

## Design contract

Create a layered benchmark evidence contract for the active
`bench/moqxprobe` + `bench/quicprobe` loop.

Every derived metric must make four things explicit:

```text
source layer + numerator + denominator/window + confidence tier
```

Examples:

- `client_payload_goodput_total_bps`
- `client_payload_goodput_sender_active_bps`
- `receiver_payload_goodput_active_bps`
- `receiver_payload_goodput_interval_p95_bps`
- `stream_payload_events_per_second`
- `datagrams_received_per_second`
- `path_baseline_tcp_bps`

Avoid ambiguous names:

- no naked `bandwidth`;
- no naked `goodput`;
- no `pkts/s` unless the source is a packet capture or QUIC packet counter;
- stream send/write counts are `payload_events`, `write_events`, or
  `send_admissions`, not packets;
- DATAGRAM counts are `datagrams`, not packets.

## Evidence layers

The contract should model at least these layers.

### Experiment lifecycle

One run bundle should have a stable run id and manifest that ties every
artifact together:

- command and arguments;
- git SHA;
- project/tool versions;
- target host/ports;
- client implementation;
- workload/profile;
- target type: `fake`, `loopback_quic`, or `remote_quic`;
- evidence tier;
- paths to sidecar artifacts;
- clock/source notes when relevant.

### Benchee invocation timing

Benchee remains the comparison engine for client implementations. Its output
answers:

- invocation latency distribution;
- invocation throughput (`ips`);
- statistical spread between implementations.

It must not be treated as receiver bandwidth or wire bandwidth unless a
derived metric explicitly says which bytes and denominator were used.

### Sender/app telemetry

`moqxprobe` should provide cheap sender-side evidence for:

- offered payload events;
- send admissions and send admission errors;
- send completion credits;
- per-stream or per-shard in-flight counts;
- queue depth / demand / backlog;
- tick lag and burst shape for paced clients;
- sender-side interval bins.

This layer answers whether the client architecture can produce work and feed
the transport without collapsing.

### Transport/NIF telemetry

Use stable transport-boundary telemetry where it exists, and extend only as
needed:

- stream send call duration and result;
- DATAGRAM send call duration and result;
- receive-event call duration and result;
- send completions / cancellations observed through normalized transport
  events;
- counts of slow calls above a configured threshold, especially around the
  `1 ms` scheduler-risk boundary.

This layer answers whether `MOQX.Transport`/`quicer` admission and completion
handling is becoming the bottleneck. It is not peer-delivery evidence.

### Receiver evidence

`quicprobe` remains the receiver-side truth for real targets. It should expose
both aggregate and interval evidence:

- first byte / first DATAGRAM timestamp;
- last byte / last DATAGRAM timestamp;
- bytes received;
- streams accepted/completed;
- DATAGRAMs received;
- receive errors;
- interval bins for bytes/DATAGRAMs/streams over time.

Receiver evidence should continue to be collected outside the measured
Benchee function. The post-run hook can wait for evidence, but the wait must
not contaminate sender timing.

### Path baseline

`iperf3` remains a preflight/path baseline, not a Benchee job.

The benchmark report should compare QUIC-derived receiver metrics against the
path baseline only when the target and path are explicit. The report should
state which baseline was used:

- TCP baseline;
- UDP baseline and configured bitrate;
- loss/jitter/retransmits;
- whether the path was local, loopback, direct remote, or relay-like.

### Host and BEAM samples

Add optional low-frequency samples for:

- BEAM scheduler utilization / run queue when available;
- process mailbox lengths for known sender roles;
- reductions and memory for known sender roles;
- GC counts/time where practical;
- host CPU and memory summary;
- network interface counters where practical.

These samples should be taken by a sampler process, not in per-event telemetry
handlers. The goal is to identify saturation and scheduler/process pressure,
not to collect perfect observability data at the cost of benchmark distortion.

### Wire evidence

Packet capture is optional and forensic, not required for every benchmark run.

When enabled, it should be captured as a sidecar and summarized separately:

- UDP bytes and packet counts;
- packet-rate windows;
- drops/retransmission-adjacent symptoms where visible;
- burstiness and pacing shape;
- capture filter, interface, and clock notes.

Wire metrics must be clearly labeled as packet-capture derived. They are the
only acceptable source for `packets_per_second` until a QUIC-stack packet
counter is explicitly added.

### Flame graphs

Flame graphs are diagnostic artifacts, not standard metrics.

Use them when a run indicates CPU-bound behavior, scheduler pressure, or a
large unexplained gap between sender, receiver, and path evidence. The bundle
should link the flamegraph artifact and note which process/command was
profiled, but ordinary benchmark summaries should not require flamegraph
generation.

## Time windows

The contract must distinguish time windows instead of averaging every metric
over the whole run.

At minimum define:

- `setup`: connect, handshake, stream creation, initial target setup;
- `sender_active`: first send attempt to last accepted send or last local send
  completion, depending on the metric;
- `receiver_active`: first receiver byte/DATAGRAM to last receiver
  byte/DATAGRAM;
- `drain`: sender done to receiver complete;
- `total_invocation`: the Benchee measured invocation;
- `post_run_evidence`: unmeasured cleanup and evidence collection;
- `steady_state`: optional middle window that excludes configured warmup and
  tail/drain portions when the workload is long enough.

Derived metrics must include the window in the name or metadata.

## Confidence tiers

Every run/report should carry an evidence tier:

- `fake`: process-model only; no QUIC or network claim.
- `loopback_quic`: local QUIC calibration; no real network claim.
- `remote_quic_no_wire`: real target with receiver evidence and iperf3
  baseline, but no packet capture.
- `remote_quic_with_wire`: real target with receiver evidence, iperf3
  baseline, host samples, and packet capture summary.
- `forensic`: a diagnostic bundle with flame graphs and deeper host/wire
  evidence.

Reports should use the tier to qualify conclusions. For example, fake-target
results can justify OTP/process-model changes, but not path saturation claims.

## Proposed artifact layout

Do not revive the old Terraform/probed/shared-ledger workflow. Stay within
the current target-based loop and write local artifacts under
`bench/moqxprobe/results/`.

Suggested bundle shape:

```text
bench/moqxprobe/results/<run-id>/
  manifest.json
  benchee.json
  delivery-evidence.jsonl
  sender-telemetry.jsonl
  receiver-intervals.jsonl
  host-samples.jsonl
  iperf3-tcp.json
  iperf3-udp.json
  capture.pcapng
  capture-summary.json
  flamegraph.svg
  report.md
```

The implementation may start with a smaller subset, but the manifest must make
missing optional artifacts explicit.

## What to build

Implement the first useful slice of this contract in the active benchmark
loop:

1. Document the layered evidence contract in `bench/moqxprobe/README.md` or a
   dedicated ADR linked from the README.
2. Add a run manifest format for `moqxprobe` benchmark runs.
3. Add explicit derived metric names for Benchee/invocation, sender/app, and
   receiver evidence layers.
4. Extend `quicprobe` receiver evidence with interval bins or add a follow-up
   issue if the implementation is too large for this slice.
5. Add report-side logic that refuses or warns on ambiguous metrics such as
   plain `bandwidth` or `pkts/s` without a packet-derived source.
6. Update the stream and DATAGRAM benchmark docs so future issue comments
   quote metrics with source layer, denominator, window, and confidence tier.

## Acceptance criteria

- [ ] A layered benchmark evidence contract is documented and linked from the
      active benchmark README.
- [ ] The contract explains why Benchee `ips`, sender telemetry, receiver
      evidence, iperf3, host samples, pcap, and flame graphs answer different
      questions.
- [ ] The contract defines metric naming rules that include source layer,
      numerator, denominator/window, and confidence tier.
- [ ] Ambiguous metric names such as plain `bandwidth`, plain `goodput`, and
      stream `pkts/s` are explicitly forbidden.
- [ ] The contract defines run lifecycle windows: setup, sender active,
      receiver active, drain, total invocation, post-run evidence, and optional
      steady state.
- [ ] The contract defines confidence tiers for fake, loopback QUIC, remote
      QUIC without wire evidence, remote QUIC with wire evidence, and forensic
      diagnostic bundles.
- [ ] `moqxprobe` can write or describe a run manifest that links Benchee
      output, evidence sidecars, iperf3 sidecars, optional sender/receiver
      interval summaries, optional host samples, optional packet captures, and
      optional flame graphs.
- [ ] `quicprobe` aggregate receiver evidence remains valid, and receiver
      interval evidence is either implemented or split into a dedicated
      follow-up with an explicit schema.
- [ ] The implementation keeps evidence collection outside timed Benchee
      functions.
- [ ] The implementation does not reintroduce Terraform, `probed`,
      release-deploy orchestration, `bench/ledger`, or `transport-bench-v1` as
      active benchmark requirements.
- [ ] The implementation does not use `Application` environment as mutable
      benchmark configuration.
- [ ] Existing fake and `quicprobe` benchmark scripts still run with explicit
      flags.

## Non-goals

- Do not build a generic dashboard in this issue.
- Do not require packet capture or flame graph generation for every run.
- Do not make pcap-derived metrics mandatory for normal caller-side iteration.
- Do not make receiver evidence part of the timed Benchee function.
- Do not treat local/fake/loopback results as real-network claims.
- Do not add high-cardinality metric labels such as payload sequence number,
  raw stream id, raw connection handle, raw peer address per event, exception
  text, or payload bytes.

## Notes

This issue should happen before the next serious optimization loop. Otherwise
we will keep debating whether a number represents client throughput, receiver
throughput, wire bandwidth, path utilization, or merely a Benchee invocation
rate.

The desired result is not "more observability" in the generic sense. The
desired result is evidence that lets us say, with the appropriate confidence
tier:

- the client process model is the bottleneck;
- the transport/NIF admission path is the bottleneck;
- the receiver is draining late;
- the path is constrained;
- the workload is bursty rather than steady;
- the measurement itself is too intrusive.

## Comments

### 2026-06-30 — Slice 1: contract documented

Implemented the documentation slice as
`docs/adr/0009-layered-benchmark-evidence-contract.md`, linked from
`bench/moqxprobe/README.md`.

The ADR adds one framing the issue gestured at but did not name: the
**closed-loop vs open-loop** distinction. Benchee is a closed-loop
service-time harness, so `ips` is invocation throughput, not wire bandwidth or
latency-under-load. Reading it as the latter is the root cause of "we can't
trust the numbers." The ADR splits measurement into two explicitly labelled
modes (closed-loop Benchee A/B vs open-loop paced sender) and names
**coordinated omission** as the reason a backpressured sender-paced benchmark
under-reports tail behavior — motivating the open-loop slice.

Remaining slices, in dependency order:

- Slice 2: `quicprobe` receiver interval bins (delivery shape over time).
- Slice 3: out-of-band BEAM sampler (scheduler util, run-queue, mailbox depth).
- Slice 4: open-loop paced sender recording offered-vs-accepted.
- Slice 5: run manifest tying artifacts together.
