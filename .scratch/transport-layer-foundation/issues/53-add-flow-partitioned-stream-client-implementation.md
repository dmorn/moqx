## Context

`bench/moqxprobe` is now the benchmark project where multiple caller-side
client implementations are preserved and compared as executable design traces.
The current fake/local winner is `sender_shards`: a Flow-fed implementation
where one GenStage dispatcher routes payload events to a bounded number of
sender workers.

That architecture proved the direction is useful, but it still owns routing
manually:

`Flow source -> FlowSenderDispatcher -> send(worker, payload_event)`

The dispatcher consumes Flow demand and then pushes events into worker
mailboxes. That is a valid experiment, but it bypasses GenStage demand at the
final shard boundary.

Flow and GenStage already provide the lower-level shape we want:

- `Flow.partition/2` materializes partitioned producers with
  `GenStage.PartitionDispatcher`;
- `GenStage.PartitionDispatcher` routes events to named partitions;
- each consumer subscribes with `partition: shard_index`;
- each partition consumer can own shard-local stream sender state and receive
  transport completion messages through normal OTP `handle_info/2`.

This issue tracks the next stream-client experiment: a fully Flow-partitioned
client that keeps the same input source and sender semantics while removing the
custom dispatcher/process-mailbox routing layer.

## Design contract

Add a new stream implementation to the `bench/moqxprobe` implementation
registry, tentatively:

`flow_partitions`

The implementation should keep the benchmark model unchanged:

- same `bench/stream_clients.exs` CLI;
- same fake and `quicprobe` target adapters;
- same Flow-produced payload events as `context_owner`, `stream_owner`, and
  `sender_shards`;
- same async stream send model and send-completion backpressure;
- same delivery-evidence post-hook model;
- no `Application` environment seam or mutable global config.

The expected data path is:

`Flow source -> Flow.partition/2 -> one GenStage shard sink per partition`

Partitioning should be deterministic and diagnosable. Prefer explicit stream
index modulo shard count over opaque stream-handle hashing:

```elixir
hash: fn event ->
  shard = rem(event.stream_index - 1, shard_count)
  {event, shard}
end
```

Each shard sink should:

- subscribe to exactly one partition with `partition: shard_index`;
- own the streams assigned to that shard;
- keep per-stream send windows and queued payload events locally;
- send asynchronously through the same transport primitives;
- receive backend send-completion messages in the same process that owns the
  shard state;
- emit local diagnostics compatible with the existing stream sender summaries.

The benchmark driver should keep lifecycle ownership explicit. Flow may finish
producing payload events before all transport send completions have arrived, so
the driver must still wait for shard completion and collect evidence after the
timed function returns.

## Acceptance criteria

- [ ] `bench/moqxprobe` contains a new named stream implementation,
      `flow_partitions`, registered alongside the existing stream
      implementations.
- [ ] The implementation uses `Flow.partition/2` or an equivalent
      GenStage-native partitioned producer path instead of manually routing
      payloads through `send(worker, event)`.
- [ ] The implementation remains Flow-fed and uses the same payload event shape
      as the other stream implementations.
- [ ] Each shard owns its stream sender state and handles send completions in
      its own OTP process.
- [ ] The implementation reports configured shard count, active shard count,
      routed/received payload count, completion count, queue/window pressure,
      and timing diagnostics comparable to `sender_shards`.
- [ ] Fake-target tests prove the implementation completes the same workload
      and receiver evidence as the existing implementations.
- [ ] A fake/local Benchee comparison records `context_owner`, `stream_owner`,
      `sender_shards`, and `flow_partitions` with the same input shape.
- [ ] Promote `flow_partitions` to current best only if it is cleaner and at
      least performance-neutral against `sender_shards`; otherwise keep it as a
      historical/rejected architecture with the evidence recorded.

## Non-goals

## Notes

The important question is not only "is it faster?" but whether it produces a
cleaner OTP/process ownership model:

- Flow handles source production and partition routing;
- GenStage demand reaches the final partition consumers;
- each shard process owns payload queue, stream sender credits, and completion
  mailbox;
- benchmark scripts compare implementations through one stable matrix.

If the experiment fails, record why and keep it in the registry as historical
or rejected evidence rather than deleting the trace.
