## Context

#49 removed the old Terraform/probed/ledger/release loop and left an active
benchmark stack with:

- `bench/quicprobe` as a simple reference peer;
- `bench/moqxprobe` as the local Benchee benchmark project;
- explicit fake/local/remote target flags;
- a persistent exe.dev target, `moqx-quicprobe-fra.exe.xyz`, running
  `iperf3` on `55202` and `quicprobe` on `55433`.

Remote smoke on 2026-06-18 proved the target is usable:

- `iperf3` TCP connected, but the current Tailscale path appeared relayed and
  only reached about 14 Mbps received with retransmits, so that value is not a
  clean path ceiling;
- `iperf3` UDP at 5 Mbps delivered with 0 loss and about 1.13 ms jitter;
- reference `quicprobe` stream echo worked VM-local and local-to-remote;
- reference `quicprobe` DATAGRAM pressure delivered 5/5 datagrams locally to
  remote with about 58.5 ms handshake and 50.3 ms first-byte latency;
- the new `moqxprobe` `stream_owner` Benchee script connected to the remote
  `quicprobe` target and completed a tiny run, but `quicprobe` server stats
  recorded accepted unidirectional streams without stream bytes before the
  client closed.

That last point is the design boundary: the current Benchee stream script is
useful for local process-model and send-completion admission comparisons, but
it is not yet a delivery-aware caller benchmark.

## What to build

Build the first delivery-aware `moqxprobe` caller benchmarks on top of the
simplified target loop.

The benchmark clients should distinguish at least two modes:

- admission/process-model mode, where the result is local send-completion and
  scheduler/process overhead;
- delivery-aware mode, where the result is tied to peer-observed stream bytes,
  DATAGRAM echoes, server stats, or another explicit receiver-side criterion.

The delivery-aware clients should still be simple caller-side transport
benchmarks, not full MOQT protocol clients yet. They should give us a reliable
loop for deciding whether a candidate caller architecture can push bytes or
DATAGRAMs into a real `quicprobe` peer before higher-level MOQT draft-14 work
starts.

## Acceptance criteria

- [ ] `bench/moqxprobe` documents the difference between admission benchmarks
      and delivery-aware benchmarks.
- [ ] Stream caller benchmarks do not report remote success solely because
      local send completions were observed.
- [ ] Stream delivery-aware runs wait for or collect a receiver-side signal:
      peer echo, server stats, a drain window/cooldown with stats verification,
      or another explicit target-side criterion.
- [ ] DATAGRAM delivery-aware runs use delivered DATAGRAM counts or echo
      counts as the delivery signal, not just local send acceptance.
- [ ] Target selection remains flag-driven and does not use mutable
      `Application` config.
- [ ] The fake target remains available for process-model calibration without
      being confused with real-network evidence.
- [ ] Remote runs record sidecar metadata: target host, ports, CA/server name,
      git SHA, `iperf3` preflight summary, Tailscale path mode when available,
      and any server stats path used.
- [ ] A small local or remote smoke proves the first delivery-aware client
      rejects or reports missing receiver-side evidence instead of silently
      passing.

## Notes

This issue should happen before drawing performance conclusions from
`moqxprobe` against remote `quicprobe`. The existing Benchee stream-owner
smoke is valuable as a connectivity and local admission check, but it is not
the benchmark that tells us whether a caller-side MOQX client successfully
fills the target link.
