## What to build

Diagnose and improve the caller-side stream/object throughput gap now that
DATAGRAM-specific tuning has been paused and mixed control scheduling has been
separated from object stream goodput.

The v1 product target is caller-side MOQ behavior: connect out, publish objects
over streams, subscribe/read streams, and keep control traffic healthy. Relay
and listener-side serving performance remain future scope. This issue tracks the
stream-throughput progress loop in the same way #40 tracked DATAGRAM progress,
but for the stream path that matters most to MOQ Lite 04 and the next protocol
work.

Current evidence says this is not primarily a DATAGRAM problem and not only a
first-control-message scheduling problem:

- #40 is closed for now: clean x86-control DATAGRAM evidence is good enough for
  the current limited draft-14 support, and MOQ Lite 04 does not use QUIC
  DATAGRAM.
- #45 control-first scheduling fixed the first-control-byte artifact, and
  `STREAM_SEND_WINDOW=64` made recurring control latency acceptable in the
  mixed shape, but object stream goodput stayed around 35 Mbps against a
  same-run reference around 117 Mbps.
- Mixed event batching reduced BEAM receive-event call count substantially, but
  did not move object goodput.
- Increasing the mixed object stream window to 1000 did not improve goodput and
  worsened control latency.
- A dirty stream-finish experiment, where mixed object payload sends opted out
  of per-payload completion tracking and object completion was based on stream
  finish, still reached only about 35.33 Mbps against a same-run reference of
  about 115.01 Mbps. It completed 32/32 object stream finishes and had zero
  pending completions, so per-payload completion bookkeeping alone is not the
  current throughput ceiling.

This issue should turn those observations into a narrower stream hardening loop:
define the right stream-only and object-stream workloads, compare them to
`quicprobe` on the same controlled path, classify the first real bottleneck, and
make the smallest measured change that moves same-run reference-relative
throughput.

## Notes

The mixed #45 workload remains useful because it exposes control health while
object streams are under pressure. This issue exists to isolate the object
stream throughput ceiling so #45 does not become an unbounded catch-all.

The next useful design decision is whether to keep using mixed object streams as
the stream workload, extract an object-stream-only workload from mixed pressure,
or use the existing pure `stream_pressure` path after aligning its semantics
with object publishing.
