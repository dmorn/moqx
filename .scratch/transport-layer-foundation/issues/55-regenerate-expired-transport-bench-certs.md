# Regenerate expired transport-bench test certs and stop expiry breakage

Status: done
Type: bug
Category: tooling

## Parent

`.scratch/transport-layer-foundation/issues/16-add-docker-compose-quic-integration-harness.md`

## Why this is needed

The slice-2 loopback smoke (issue 54) failed its first attempt because the
checked-in test certificate `.tmp/transport-bench-certs/server.pem` had
expired:

```
notAfter = May 27 08:25:04 2026 GMT
```

The QUIC handshake aborted with
`{:error, {:transport_down, %{error: 301, status: :expired_certificate}}}`.
The smoke only proceeded because fresh certs were generated by hand into a
scratch directory.

This is a fixture-expiry problem, not a code defect, but it silently breaks any
local loopback QUIC run, the moqxprobe `target=quicprobe` loopback path, and
likely the `mix test --only integration` harness, until someone notices the
handshake error and regenerates certs manually. Remote `reform` runs are
unaffected because reform uses its own CA.

## What to build

1. Provide a single documented command (mix task or script) that provisions a
   fresh local CA + server certificate for loopback QUIC benchmarks, with SANs
   covering `localhost` and `127.0.0.1`, into the expected fixture path.
2. Give the generated certificate a long validity (for example several years)
   so routine expiry stops interrupting local work, and make regeneration
   idempotent.
3. Decide whether the `.tmp/transport-bench-certs` material should remain
   checked in at all, or be generated on demand and git-ignored. Prefer
   generate-on-demand so there is no committed expiring artifact.
4. If certs are generated on demand, ensure the moqxprobe/quicprobe loopback
   docs and the integration harness reference the provisioning step.

## Acceptance criteria

- [ ] A documented, idempotent command provisions loopback QUIC certs with
      `localhost` + `127.0.0.1` SANs into the path the benchmarks expect.
- [ ] Loopback QUIC handshakes succeed against the provisioned certs.
- [ ] Either the committed certs are replaced with long-lived ones, or the
      fixture is generated on demand and git-ignored with no committed
      expiring artifact.
- [ ] The loopback benchmark / integration docs point at the provisioning
      step.

## Non-goals

- Changing `reform` or any remote target CA handling.
- Reworking the docker-compose integration harness beyond cert provisioning.

## Comments

### 2026-07-01 — Resolved

Root cause: the only cert generator was the inline recipe in
`docker-compose.integration.yml`, which minted the CA and server cert with
`-days 7` and reused existing files without an expiry check — so once generated,
the harness served week-old, then expired, certs indefinitely. The expired
`.tmp/transport-bench-certs/server.pem` the slice-2 smoke tripped on was an
orphaned manual dir referenced by nothing in the repo.

Fix:

- Added `scripts/gen-loopback-certs.sh`: a shared, idempotent generator that
  mints a ~100-year (`-days 36500`) self-signed CA + server cert for
  `localhost`/`127.0.0.1`/`::1` (+ docker service names), reused unless missing
  or nearly expired (`openssl x509 -checkend`). Verified: `notAfter` 2126, all
  SANs present, reuse path works, portable across macOS LibreSSL and alpine.
- `docker-compose.integration.yml` now calls the shared script instead of the
  inline `-days 7` recipe (single source of truth).
- Documented the manual loopback step in the root README and
  `bench/moqxprobe/README.md`.
- Deleted the orphaned `.tmp/transport-bench-certs/` dir.

Certs are still not committed to git; `.tmp/` remains local/ignored. The
long-lived cert is acceptable because it only authenticates a loopback
handshake; remote targets (reform) use their own CA and are untouched.
