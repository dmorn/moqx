## Context

`bench/quicprobe` already records useful receiver-side facts for a connection:
accepted bidirectional and unidirectional streams, completed streams, stream
bytes received, stream bytes echoed, DATAGRAMs received, DATAGRAMs accepted for
echo, byte counts, first-byte latencies, and error counters.

Today those facts are not yet a clean benchmark contract for `moqxprobe`.
Client-side send completion proves local admission/backpressure behavior, but
it does not prove that a remote peer observed object bytes or DATAGRAMs. For
unidirectional object stream tests in particular, `quicprobe` drains bytes
without echoing them, so the server is the source of delivery truth.

The target should behave more like `iperf3`: a long-running server reports each
completed connection or benchmark run as receiver-side evidence.

## Design

Add a small, explicit run evidence surface to `quicprobe`.

Initial shape:

- keep `quicprobe server` as a long-running process;
- emit one structured JSON record for each completed connection/run on stdout
  and, when configured, to the existing stats output path;
- include a monotonic sequence number, timestamps, remote/local addresses, ALPN,
  stream counts, stream bytes received, stream bytes echoed, completed stream
  count, DATAGRAM receive/echo counts, byte counts, first-byte latencies, and
  error counters;
- treat one client benchmark connection as one run for the first iteration;
- make missing receiver evidence explicit: no stats record, zero received
  bytes, non-zero receive errors, or incomplete expected counts must not be
  reported as delivery success.

Automation surface:

- stdout JSONL remains useful for local operation and systemd/journal
  inspection;
- expose the same records through an always-on tiny read-only HTTP API because
  it materially simplifies `moqxprobe` automation against both local and
  persistent remote targets;
- the HTTP API should expose records from an in-memory ring buffer using simple
  endpoints for health, latest sequence, and records since sequence number;
- no remote run orchestration, authentication, or control plane should be added
  here.

Run identity:

- first phase can rely on one QUIC connection per benchmark run plus sequence
  numbers and timestamps;
- if that becomes ambiguous, add an explicit run identifier carried by the
  benchmark payload/control prelude, but do not invent a full MOQT protocol
  handshake for `quicprobe`.

## Acceptance criteria

- [x] `quicprobe server` emits a structured receiver-side evidence record for
      each completed connection/run.
- [x] Evidence records distinguish bidirectional stream echo, unidirectional
      stream drain, and DATAGRAM echo semantics.
- [x] Evidence records contain enough counters for `moqxprobe` to verify
      delivery for draft-14 control, object stream, object DATAGRAM, and mixed
      control-plus-object profiles.
- [x] Local operation can inspect evidence through stdout JSONL or an explicit
      stats output file.
- [x] HTTP API is always enabled for `quicprobe server`; stdout JSONL, journal,
      and `--stats-output` remain optional/debug evidence surfaces.
- [x] Evidence records are emitted in a form that `moqxprobe` target adapters
      can consume after timed workloads without including remote reads in
      Benchee hot-path timing. The actual adapter implementation remains in
      `.scratch/transport-layer-foundation/issues/50-build-delivery-aware-moqxprobe-caller-clients.md`.
- [x] `go test ./...` covers the evidence record formatting and HTTP evidence
      API behavior.

## Notes

Do not make `quicprobe` a MOQT implementation. It remains a simple QUIC peer
whose behaviors map onto MOQT-shaped transport profiles:

- bidirectional stream echo for control or transaction-like traffic;
- unidirectional stream drain for object/group stream ingress;
- DATAGRAM echo for unreliable object DATAGRAM paths.

### 2026-06-18 implementation and verification

Implemented `quicprobe-server-run-evidence-v1` records with
`record_type=server_run_evidence`. Each completed connection now emits compact
JSON to server stdout and appends the same record to `--stats-output` when
configured.

The record includes run sequence, timestamps, addresses, ALPN, explicit
semantics for bidirectional streams (`echo`), unidirectional streams (`drain`),
and DATAGRAMs (`echo`), plus receiver-side stream/DATAGRAM counters and error
state. QUIC application close code 0 from the remote peer is treated as normal
connection termination, not as failed receiver evidence.

### 2026-06-18 always-on evidence HTTP API

Added a tiny read-only evidence HTTP API to `quicprobe server`. The API is
always started with the server; `--evidence-http-addr` only controls the bind
address and defaults to `:55434`.

Endpoints:

- `GET /healthz`
- `GET /evidence/latest`
- `GET /evidence/runs?after_sequence=N`

The API serves the same `server_run_evidence` records from a bounded in-memory
ring buffer while preserving stdout and `--stats-output` JSONL behavior.
`moqxprobe` now prefers this HTTP API for `target=quicprobe` evidence
collection and falls back to a local JSONL path when explicitly requested.

- local API health returned `latest_run_sequence=0` before any client run;
- local moqxprobe stream-owner smoke against quicprobe using only HTTP
  evidence produced 1/1 valid delivery evidence records;
- API `GET /evidence/latest` reported sequence 1 after the smoke;
- API `GET /evidence/runs?after_sequence=0` returned the matching
  `server_run_evidence` record.
